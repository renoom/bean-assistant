# 萤火镇设计文档

> 状态：方案草案 v0.1  
> 目标 Stage：`town:ai-meadow`  
> 本文先确定产品模型、数据边界和实施顺序，不在这一阶段直接堆叠玩法代码。

## 1. 产品目标

萤火镇不是一张带有几个点击热点的背景图，而是一个持续存在、可以发展的 2D 像素小镇。玩家和助手都作为镇民进入同一个世界，拥有位置、外观、资产和行为，可以探索、交谈、采集、制作、建造，并逐步改变小镇。

核心体验是：

1. 玩家先进入一个只有自然地形的世界。
2. 助手以自己的身份进入，并选择已有装扮或创建新装扮。
3. 玩家与助手使用同一套世界规则移动、互动和建造。
4. 房屋、工坊、家具和公共设施由镇民逐步建成，而不是预先画死在地图背景中。
5. 世界状态持续保存；重新进入以后，建筑、资源、人物位置和发展结果仍然存在。

## 2. 当前版本与目标版本的差距

| 领域 | 当前版本 | 目标版本 |
|---|---|---|
| 地图 | 一张带建筑的概念背景图 | 无建筑的可游玩自然地图，带网格、碰撞、寻路和建造判定 |
| 空间 | 归一化 `x/y` 坐标，角色瞬时或直线移动 | 世界坐标与瓦片坐标，路径规划、动态障碍和朝向动画 |
| 场景物件 | 固定热点和图片 | 有占地、碰撞、入口、状态、交互动作的世界实体 |
| 角色形象 | 每个助手一张精灵表，直接存绝对路径 | 每个 Stage 多套装扮；一套装扮可同时包含立绘、世界动画和图标 |
| 生图能力 | 服务端工具 `draw_sprite_animation` 直接暴露给助手 | 不注册为 LLM 工具，只提供异步媒体生成接口；Godot 对外提供 `dress_up` 和 `create_object` |
| 入场 | 每次没有图片时生成序列帧 | 必须装备一套兼容当前 Stage 的装扮；已有装扮可以直接复用 |
| 互动 | `interact_at` 发送自然语言事件 | 由游戏规则执行的移动、采集、建造、使用、对话和生产行为 |
| 存档 | Godot 保存场景、物件和助手位置 | 世界快照 + 追加事件日志 + 版本号，支持冲突检查和迁移 |

## 3. 概念边界

为了避免再次把 Channel、Stage 和地图混在一起，后续统一使用下面的定义。

| 概念 | 含义 |
|---|---|
| Assistant | 助手的全局身份、会话、人格和记忆 |
| Channel | HTTP/WS 通信方式，只传输消息和事件 |
| Stage | 助手当前所处的语义环境。萤火镇整体是一个 Stage |
| Zone | Stage 内的空间区域，例如湖泊、森林、中央草地、海滩 |
| World | 萤火镇的持久化游戏状态 |
| Appearance | 某个助手在某个 Stage 下的一套装扮 |
| WorldObject | 放置在世界里的建筑、家具、资源点或装饰物 |

“每个场景的形象独立”在本设计中落实为“每个 Stage 的装扮库独立”。湖泊、森林和海滩是萤火镇内部的 Zone，不会在进入不同 Zone 时强制换装，但助手可以主动选择适合区域或活动的另一套装扮。

## 4. 萤火镇地图

### 4.1 地图不能只有一张画

可游玩的地图必须同时包含视觉资源和语义数据。不能让程序从最终 PNG 的颜色猜测哪里能走、哪里能建造，也不能让生成模型自由决定碰撞体。

第一版地图资源包定义为：

```text
assets/town/ai_meadow/
├── terrain.png             # 供玩家看到的完整像素地形，无任何建筑
├── terrain.json            # 尺寸、瓦片、区域和语义格数据
├── minimap.png             # 小地图
├── masks/
│   ├── walkable.png        # 调试用可行走区域图
│   ├── buildable.png       # 调试用可建造区域图
│   └── water.png           # 调试用水域图
└── town_world.tscn         # Godot 地图场景
```

`terrain.png` 是真正使用的游戏地图美术，不再是带透视建筑和文字标识的概念图。`terrain.json` 才是碰撞、寻路和建造规则的权威来源。三张 mask 主要用于开发检查，不作为运行时判断的唯一来源。

### 4.2 第一版尺寸

| 属性 | 设计值 |
|---|---:|
| 逻辑网格 | 160 × 112 格 |
| 基础瓦片 | 16 × 16 像素 |
| 地图原始尺寸 | 2560 × 1792 像素 |
| 显示方式 | 像素整数缩放，Camera2D 移动 |
| 坐标原点 | 左上角 `(0, 0)` |
| 存档坐标 | 瓦片坐标；渲染时换算为世界像素坐标 |

该尺寸足够容纳完整自然区域和早期小镇，又不会让第一版的寻路、存档和地图制作失控。以后可以把多个同规格地图拼成区域，但第一版先把一个连续世界做完整。

### 4.3 自然区域布局

地图初始状态不放房屋、商店、工坊、码头、桥梁、喷泉或公告栏。只存在自然地形和少量不可建造的自然障碍。

| Zone | 位置与用途 | 初始规则 |
|---|---|---|
| 中央草甸 | 地图中部的大面积缓坡和平地，是未来镇中心 | 大部分可行走、可建造 |
| 萤火湖 | 西北部湖泊，岸线不规则，带一个小岛 | 水面不可行走、不可建造；岸边可钓鱼 |
| 月溪 | 从湖泊流向南部海岸的浅河 | 深水阻挡；浅水点以后可造桥 |
| 青影森林 | 北部和东北部 | 林下可行走，树木格阻挡；清理后部分格可建造 |
| 南风海滩 | 南部海岸，包含沙滩、潮池和海水 | 沙地可行走；只有稳定沙地允许轻型建筑 |
| 东部丘地 | 东侧较高地势，岩石和草坡较多 | 可采石；陡坡阻挡；少量平台可建造 |
| 西南湿地 | 湖溪与海岸之间的湿地 | 通行较慢，默认不可建造，可采集特殊资源 |

初始道路只保留少量自然土径，用于引导玩家认识区域。正式石路、木栈道、桥和广场都由玩家或助手建造。

### 4.4 地形语义

每个格子可同时拥有多个标记，而不是只分“能走”和“不能走”。

| 标记 | 含义 |
|---|---|
| `walkable` | 普通角色能否进入 |
| `buildable` | 是否允许建筑占用 |
| `water` | 是否属于水域 |
| `shore` | 是否允许钓鱼、取水等岸线互动 |
| `forest` | 是否属于森林生态区 |
| `resource` | 是否允许生成木材、石料、草药等资源 |
| `protected` | 永久自然地貌，不能被普通建造覆盖 |
| `slow` | 湿地、浅水等降低移动速度的地形 |

运行时由 `TownTerrain` 读取这些标记：

- `AStarGrid2D` 根据 `walkable` 和建筑占用生成路径。
- 建造校验同时检查 `buildable`、占用状态、坡度和入口可达性。
- 建筑落成后只更新动态占用层，不修改基础地形文件。
- 角色和建筑碰撞由语义格生成，视觉图片不承担规则判断。

### 4.5 美术要求

- 原创温暖像素风，统一俯视角和光照方向。
- 森林、草甸、湖泊、河流、海滩和丘地之间有自然过渡。
- 不包含建筑、文字、人物、UI、网格线和地点图标。
- 可建造草地必须留下足够连续空地，不能用大量纯装饰堵满。
- 海岸、悬崖、深水、树木和岩石的视觉边界必须与语义格大致一致。
- 最终交付 PNG，而不是用脚本临时绘制的占位图。

## 5. 装扮系统

### 5.1 现有工具的位置

当前 `draw_sprite_animation` 是助手进程启动时注册的服务端工具。它不属于 WsChannel，也不是萤火镇 Stage 自己提供的命令。Codex 和 imagegen 在助手服务端运行，Godot 只负责使用结果。

这个部署位置是合理的：生成需要模型、凭证、磁盘和较长任务生命周期，不应该塞进 Godot 客户端。但公开给助手的能力名称和数据模型需要改变。

### 5.2 生图改为隐藏的媒体生成能力

`draw_image` 和 `draw_sprite_animation` 都不再注册到 Agent 的工具表。它们下沉为一个普通的异步服务接口，例如：

```text
POST   /api/media/jobs              创建生成任务
GET    /api/media/jobs/:jobId       查询进度和结果
DELETE /api/media/jobs/:jobId       取消任务
GET    /api/assets/:assetId         下载生成资源
```

创建请求使用稳定的能力类型，而不是把提示词协议泄漏给客户端：

```json
{
  "kind": "appearance",
  "specVersion": 1,
  "request": {
    "stageId": "town:ai-meadow",
    "name": "萤火镇日常装",
    "description": "红帽橘猫剑客，适合田园小镇生活",
    "basedOn": "可选，已有 appearanceId"
  }
}
```

接口负责调用 Codex/imagegen、格式校验、生成 manifest、资产存储和下载。它不出现在 system prompt 或工具 schema 中，NPC 不知道底层使用哪种模型、提示词或供应商。

长期看，这个接口适合成为 Console 管理的共享媒体服务；第一版也可以暂时挂在 assistant HTTP 服务上。即使挂在 assistant 进程里，它仍然只是供 Godot 调用的 HTTP 能力，不注册为 Agent 工具。

### 5.3 `dress_up` 是 Godot 提供的 Stage 指令

当前 Stage 通过 Bridge 向助手公开 `dress_up`，中文语义为“为自己准备一套候选装扮”。建议输入：

```json
{
  "action": "create",
  "stageId": "town:ai-meadow",
  "name": "萤火镇日常装",
  "description": "红帽橘猫剑客，适合田园小镇生活",
  "basedOn": "可选，已有 appearanceId"
}
```

第一版支持两种生成方式：

- `create`：创建一套全新装扮。
- `adapt`：以已有装扮为角色参考，创建服装或场景适配变体，尽量保持身份特征。

执行链路为：

1. 助手调用 `stage_action.dress_up`，表达想要的装扮。
2. Godot 调用媒体生成接口创建异步任务。
3. 资源完成后由 Godot 下载到 `user://` 缓存并校验 manifest、尺寸和哈希。
4. Godot 把它登记为候选装扮，向助手发送 `appearance_candidate_ready` 场景事件。
5. 助手调用 `equip_appearance` 明确采用，或调用 `discard_candidate` 放弃，也可以再次 `dress_up` 要求修改。

`dress_up` 只生成候选项，不自动换装。“生成”和“采用”是两个动作。这样助手能够反悔，玩家也有机会在真正应用前预览。

“列出已有装扮”和“装备装扮”继续由 `list_appearances` 和 `equip_appearance` 完成。

### 5.4 一套装扮包含多种表现资源

```json
{
  "id": "appearance_xxx",
  "ownerAssistantId": "assistant-xxx",
  "stageId": "town:ai-meadow",
  "name": "萤火镇炼金术师",
  "version": 1,
  "slots": {
    "portrait": {
      "image": "portrait.png",
      "aspect": "4:7"
    },
    "worldSprite": {
      "manifest": "world-animation.json"
    },
    "icon": {
      "image": "icon.png"
    }
  },
  "tags": ["town", "daily", "alchemy"]
}
```

其中：

- `portrait` 用于对话框、人物详情和近景互动。
- `worldSprite` 用于地图上的四方向待机与行走动画。
- `icon` 用于小地图、队伍列表和通知；第一版可以从立绘裁切生成。
- 后续可以增加情绪立绘、工作动作和特殊动画，不破坏现有协议。

生成顺序应先建立角色主参考图，再用该参考图生成世界精灵表，以提高立绘和小人之间的身份一致性。

### 5.5 每个 Stage 多套装扮

装扮归属于 `assistantId + stageId`，每个 Stage 可以保存多套，且同一时刻装备其中一套：

```text
Assistant Identity
└── StageAppearanceLibrary
    ├── town:ai-meadow
    │   ├── 日常装（已装备）
    │   ├── 雨天装
    │   └── 炼金工作服
    └── vn:castle
        └── 宫廷礼服
```

入场规则：

1. 当前 Stage 已有已装备且资源有效的装扮：直接复用，不生成新图。
2. 有兼容装扮但没有已装备项：助手选择一套并装备。
3. 没有任何兼容装扮：必须调用 `dress_up` 创建一套。
4. 已经有装扮时，助手仍可根据季节、工作或自己的意愿主动换装。
5. 断线重连只恢复已装备装扮，不重复生成。

Stage 存档只记录 `appearanceId`，不再把某张图片绝对路径当作角色身份。资源文件由助手侧的装扮库管理。

### 5.6 图片识别能力与候选结果

当前工程的视觉输入直接走 DSH 原生多模态链路：客户端向 `POST /api/message` 同时提交文本和图片，服务端先通过 `attachment-local` 校验并持久化图片，再将文本块和 `image` attachment block 作为同一条用户消息加入助手的唯一持久会话。图片会和系统提示词、Stage 上下文及历史消息一起发送给当前 provider/model，不存在独立的“识图模型”或 NPC 可调用的识图工具。每个助手的 WebUI 在消息输入框旁提供图片选择与预览。

实际能否理解图片取决于当前 DSH adapter 和模型：`llm-pi-ai` 能把 attachment 解析成供应商原生图片内容；DeepSeek 官方 chat-completions adapter 会明确返回 `UNSUPPORTED_CONTENT`。因此，萤火镇需要为承担视觉判断的助手选择声明并实际支持 image input 的模型，不能静默退化成只发送文字或另行调用不相关模型。

候选结果不能只给助手一个文件路径。媒体生成接口必须同时返回：

```json
{
  "candidateId": "candidate_xxx",
  "assets": ["asset_portrait", "asset_world_sprite"],
  "visualSummary": "红色兜帽、深棕长发、炼金药瓶……",
  "qualityReport": {
    "formatValid": true,
    "transparent": true,
    "frameConsistency": 0.91,
    "problems": []
  },
  "manifest": {}
}
```

第一版由媒体生成流程产生 `visualSummary`、`qualityReport`，Godot 同时把候选图片作为 DSH attachment 送入助手会话并向玩家展示真实预览。使用支持视觉的当前模型时，助手可以结合真实图片和结构化报告决定采用、修改或放弃。

### 5.7 远程资产传输

当前绝对文件路径只在助手和 Godot 位于同一台机器时有效，与“助手云端化”的目标冲突。装扮和物件资源最终统一使用：

```text
assetId + sha256 + mimeType + size + downloadUrl
```

Godot 首次看到资源时下载到本地缓存，校验哈希后加载。Stage 存档保存 `assetId` 和哈希，不保存云端机器的绝对路径。本地开发阶段仍可兼容绝对路径。

## 6. 建造与世界物件

### 6.1 生成和放置分开

造房子也沿用“隐藏能力生成资产，Stage 执行世界规则”的边界：

1. 助手调用 Godot 提供的 `stage_action.create_object`，描述想创建的物件。
2. Godot 调用媒体生成接口，等待并下载物件资源包。
3. Godot 登记候选物件，向助手发送 `object_candidate_ready`，其中包含结构化视觉摘要、尺寸、用途、占地和质量报告。
4. 助手决定是否使用该候选项；不满意可以放弃或重新生成。
5. 助手通过 `stage_action.preview_build` 请求合法位置和放置预览。
6. 玩家确认，或规则允许助手自主决策后，调用 `stage_action.place_object`。
7. Godot 检查资源、占地、碰撞、材料、权限和入口路径。
8. 成功后写入世界状态并广播 `object_built` 事件。

生成模型不能直接修改世界，也不能自行声明任意碰撞形状。它负责美术和语义描述，最终占地与碰撞由标准模板和 Godot 校验产生。

### 6.2 世界物件资源包

```json
{
  "id": "object_cottage_xxx",
  "kind": "building",
  "name": "林间炼金小屋",
  "visual": {
    "image": "building.png",
    "anchor": "bottom-center"
  },
  "footprint": {
    "width": 7,
    "height": 5,
    "entrance": { "x": 3, "y": 4 }
  },
  "collisionTemplate": "solid_except_entrance",
  "interactions": ["enter", "inspect"],
  "tags": ["house", "alchemy"]
}
```

第一版支持四类对象：

| 类型 | 示例 | 规则特点 |
|---|---|---|
| `building` | 房屋、工坊、仓库 | 大占地、有入口、阻挡路径 |
| `facility` | 工作台、水井、路灯 | 小占地、提供交互或生产能力 |
| `furniture` | 桌椅、箱子、招牌 | 可移动，可属于室内或室外 |
| `decoration` | 花坛、雕塑、旗帜 | 主要改变外观，也可有简单互动 |

树木、石头、草药等自然资源由世界规则生成，不使用生图工具逐个创建。

### 6.3 建造校验

一次建造至少通过以下检查：

- 所有 footprint 格都具有 `buildable`。
- 不覆盖水面、保护地形、资源节点或其他对象。
- 建筑入口对应的相邻格可行走。
- 放置后不会把必要通路完全堵死。
- 对象资源包版本与 Stage 支持版本兼容。
- 玩家确认策略允许本次消耗和永久世界修改。
- 使用 `worldRevision` 做乐观并发检查，避免两个助手同时占用同一位置。

拆除、移动和升级也走同一套世界命令与校验，不直接操作 Godot 节点。

## 7. 玩家与助手能力

最终玩家和助手应调用同一个 `TownWorld` 领域层。输入方式不同，但规则一致。

### 7.1 第一阶段能力

| 能力 | Stage 命令 | 说明 |
|---|---|---|
| 观察 | `observe_area` | 返回附近地形、角色、对象和可互动项 |
| 移动 | `move_to` | 使用瓦片坐标、对象或 Zone 作为目标，并走寻路 |
| 说话 | `say` / `say_to` | 在世界内公开或定向交谈 |
| 生成装扮 | `dress_up` | 让 Godot 请求媒体能力创建候选装扮，不直接装备 |
| 装扮 | `list_appearances` / `equip_appearance` | 查看和装备当前 Stage 的装扮 |
| 查看地图 | `inspect_map` | 获取 Zone 摘要和已发现地点 |
| 创造物件 | `create_object` | 让 Godot 请求媒体能力创建候选物件，不直接放置 |
| 放置预览 | `preview_build` | 验证占地并返回候选位置 |
| 建造 | `place_object` | 放置已生成的对象资源 |
| 使用物件 | `interact_with` | 使用门、设施、家具或资源点 |

### 7.2 后续生活循环

在地图和建造稳定以后，再依次加入：

1. 采集：木材、石料、草药、鱼和农作物。
2. 背包与仓库：资源归属、容量和转移。
3. 制作：配方、工具、家具和建筑材料。
4. 农业：整地、播种、浇水、生长与收获。
5. 生产设施：工坊、厨房、炼金台和商店。
6. 委托与交易：镇民之间形成真实协作需求。
7. 时间与天气：影响装扮、作物、资源和活动。

不要在地图基础和世界状态尚未稳定时同时实现这些系统，否则每个系统都会依赖不稳定的坐标、对象和存档结构。

## 8. 世界状态与执行边界

Godot 中的 `TownWorld` 是当前萤火镇的权威状态。助手会话、提示词和记忆不能代替游戏存档。

```text
TownWorld
├── worldRevision
├── terrainId / terrainVersion
├── actors
│   └── assistantId → appearanceId, tile, facing, activity
├── objects
│   └── objectInstanceId → assetId, tile, rotation, state, owner
├── resources
├── discoveries
└── eventLog
```

每个修改命令包含：

- `actionId`：用于幂等，重试不会重复建造。
- `expectedRevision`：用于发现并发冲突。
- `actorId`：明确是谁执行。
- 结构化参数：坐标、对象 ID、数量等。

执行成功后 `worldRevision + 1`，生成语义事件并保存。其他助手收到的是“某人在某处建成了一座房子”，而不是底层节点变化。

存档采用定期完整快照加追加事件日志。快照用于快速恢复，事件日志用于审计、调试和将来的有限撤销。

## 9. 上下文与工具注入

萤火镇地图很大，不能每轮把整张地图、全部建筑和全部装扮重复塞进上下文。

Stage 常驻上下文只包含：

- 当前 Stage ID、名称和规则版本。
- 助手自己的身份、已装备装扮和当前位置。
- 当前所在 Zone 与附近对象的极短摘要。
- 稳定的能力列表和行为约束。

详细世界信息通过 `observe_area`、`inspect_map`、`list_appearances` 等工具按需读取。场景发生变化时发送小型结构化事件，不重复注入完整世界快照。这样既保持“助手像人一样处于一个环境中”，也避免频繁场景信息造成上下文和缓存浪费。

NPC 只看到当前 Stage 通过 Bridge 提供的 `dress_up`、`create_object`、装备、建造和互动指令。真正的图片生成是 Godot 调用的外部媒体能力，不进入 Agent 工具表。Channel 继续只负责通信。

## 10. Godot 模块拆分

建议从当前单个 `stage.gd` 逐步拆成：

```text
core/town/
├── town_world.gd             # 权威世界状态与命令入口
├── terrain_map.gd            # 地形格与 Zone 查询
├── pathfinder.gd             # AStarGrid2D、动态占用更新
├── build_validator.gd        # 建造规则
├── world_object.gd           # 对象实例数据
├── actor_state.gd            # 角色位置、朝向、活动和装扮引用
├── appearance_registry.gd    # 装扮资源解析与缓存
├── asset_cache.gd            # assetId 下载、哈希校验、本地缓存
├── town_store.gd             # 快照、事件日志和 schema 迁移
└── town_events.gd            # 对外语义事件

scenes/town/
├── town_stage.tscn
├── terrain_renderer.gd
├── actor_renderer.gd
├── object_renderer.gd
├── build_preview.gd
└── town_camera.gd
```

领域层只处理格子、实体和规则；渲染层只把状态变成 Godot 节点。这样地图图片、角色动画和建筑素材都能更换，而不改变存档规则。

## 11. 实施顺序

### 里程碑 1：可行走的自然地图

- 生成并确认萤火镇地形美术稿。
- 落地 `terrain.png + terrain.json`。
- 实现 Camera2D、瓦片坐标、可行走/可建造/水域语义。
- 实现 AStarGrid2D 寻路和碰撞。
- 移除当前背景中预画的建筑与八个假热点。
- 角色可以从中央草甸走到森林、湖岸和海滩。

### 里程碑 2：Stage 级装扮库

- 从 Agent 工具表移除 `draw_image` 和 `draw_sprite_animation`，改造成异步媒体生成 HTTP 接口。
- 由 Godot Stage 提供 `dress_up`、候选结果通知和 `equip_appearance`。
- 一次生成同一角色的立绘和世界序列帧。
- 候选图片作为 DSH attachment 进入同一会话，并附带结构化视觉摘要和质量报告。
- 加入 Appearance manifest、装扮列表和装备命令。
- Stage 存档改存 `appearanceId`。
- 重连复用装扮；每个 Stage 可保存、切换多套。

### 里程碑 3：世界物件与建造

- 扩展媒体生成接口以支持 `world-object` 资源包，不向 Agent 注册生成工具。
- 由 Godot Stage 提供 `create_object` 和候选物件通知。
- 实现标准 footprint、入口与碰撞模板。
- 实现建造预览、放置、移动和拆除。
- 先支持小屋、工作台、箱子和路灯四种模板。

### 里程碑 4：互动与发展循环

- 采集、背包、配方和生产设施。
- 农业、钓鱼和基础交易。
- 委托、共同建设和镇民事件。
- 时间、天气与装扮适配。

## 12. 下一步：地图里程碑的验收标准

下一步只做里程碑 1，完成后再进入装扮重构。验收标准如下：

1. 地图是一张可直接运行的原创像素地形 PNG，不包含建筑或文字。
2. 湖泊、河流、森林、中央草甸、丘地、湿地和海滩在视觉上清楚可辨。
3. Godot 使用 Camera2D 浏览完整地图，不再把整张图缩进一个窗口。
4. 至少存在 `walkable`、`buildable`、`water`、`protected` 四类可视化调试层。
5. 角色点击目标位置后沿合法路径行走，不能穿过深水、树木和悬崖。
6. 中央草甸有足够空间放置至少 20 座中型建筑。
7. 海滩和森林具有可探索空间，但不会被误判为大面积可建造土地。
8. 地图语义通过自动检查：坐标范围有效、出生点可达、主要 Zone 互通、没有越界格。

完成这一里程碑后，萤火镇才从“概念背景”变成“游戏世界的地基”。
